# TennisFinder System Blueprint

## 1. Core Architecture: The "Split-Brain" Data Flow
TennisFinder operates as a distributed system where Convex handles the real-time state and Python handles the intelligence.



- **Primary Source of Truth:** Convex (NoSQL).
- **Inference Engine:** Python FastAPI (Scikit-learn/Tuned Model).
- **The Bridge:** Convex Actions using `fetch` to localtunnel/production AI endpoints.

## 2. Shared Data Model & Safety Protocols
- **Auth Boundary:** All B2C actions (Racket listing, booking) are scoped to the `userId` provided by `@convex-dev/auth`.
- **Global Time:** All timestamps are Unix Integers (`Date.now()`).
- **Marketplace Logic:** - `predicted_sold_price` (Optional): Generated by AI.
    - `ai_label` (Optional): Determined by comparing `user_price` vs `predicted_sold_price`.

## 4. Fault Awareness & Disaster Recovery
- **AI Offline:** If the Python service fails, the system must allow "Graceful Degradation." Items are listed with an `AI Offline` label instead of blocking the user.
- **Schema Drift:** Any modification to `schema.ts` is considered a "Breaking Change" and requires immediate synchronization of the `_generated/` folders across all monorepo packages.
